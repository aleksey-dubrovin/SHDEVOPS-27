
# Заключение

## Итоги работы

В рамках дипломной работы я разработал и развернул полноценный
DevOps-стек в облаке Yandex Cloud. Проект охватывает все этапы
жизненного цикла приложения: от подготовки инфраструктуры как кода
до автоматического деплоя и мониторинга.

## Достигнутые результаты

### Инфраструктура

- Спроектирована модульная архитектура Terraform: 6 модулей
  (`vpc`, `security-group`, `iam`, `k8s-cluster`, `compute`,
  `observability`), каждый со своим интерфейсом.
- Настроен S3 backend для хранения state с версионированием.
- Создано 9 подсетей в 3 зонах доступности (публичные, приватные,
  управляющие).
- Развёрнут NAT-шлюз, приватный эндпоинт S3, Container Registry,
  Audit Trails, Logging Group.
- Сервисному аккаунту назначены только необходимые роли, без
  использования суперпользовательских прав.

### Kubernetes

- Развёрнут гибридный кластер: управляемый региональный мастер
  и 2 внешних worker-узла на прерываемых ВМ.
- Включён туннельный режим Cilium, решена проблема с MTU.
- Настроен Bastion-хост и SSH-доступ через ProxyJump.
- Развёрнут NLB и Ingress NGINX с фиксированными портами.
- Реализовано централизованное управление секретами через
  data-driven реестр.

### Приложение и CI/CD

- Создан отдельный репозиторий для приложения с Dockerfile
  на `nginx:alpine`.
- Настроена автоматическая сборка образа при коммите в main
  и при создании тега.
- Построена сквозная цепочка: тег в приложении → сборка образа →
  `repository_dispatch` → деплой в кластер.
- Все три репозитория имеют независимые пайплайны с правильными
  триггерами.

### Мониторинг и алертинг

- Развёрнут стек `kube-prometheus-stack`: Prometheus, Grafana,
  Alertmanager, node-exporter, kube-state-metrics.
- Grafana доступна по HTTPS на `monitoring.dubrovins.ru`.
- Alertmanager настроен через `configSecret` (актуальный подход
  для текущей версии chart).
- Реализована интеграция с MAX Bot для отправки уведомлений.
- Проверена сквозная доставка алертов в мессенджер.

### Аудит и логирование

- Настроены Audit Trails для сбора всех действий с облачными
  ресурсами.
- Настроена Logging Group для сбора логов Kubernetes кластера.
- Оба потока данных объединены в одну группу для удобного
  просмотра и анализа.

## Что было самым сложным

1. **Работа с прерываемыми ВМ.** Потеря публичного IP при
   перезапуске, слипание подов на одном узле, OOM-killer.
   Решено через резервирование статического IP, topology spread
   constraints и pod anti-affinity.
2. **Проблемы совместимости.** Версия `kube-prometheus-stack`
   91.4.1 не поддерживает устаревший способ конфигурации
   Alertmanager через `alertmanager.config`. Пришлось перейти
   на `configSecret`.
3. **Yandex Container Registry и Docker Buildx.** По умолчанию
   buildx добавляет attestation-данные в манифест образа,
   которые Yandex Registry не читает. Решено параметрами
   `provenance: false` и `sbom: false`.
4. **Ограничения Cilium tunnelled mode.** Мастер не может
   достучаться до admission webhook пода ingress-nginx.
   Пришлось отключить webhook для ingress-nginx и подобрать MTU.
5. **Отсутствие PVC на внешних узлах.** CSI-драйвер Yandex Cloud
   не поддерживает внешние узлы, PVC остаются в `Pending`.
   Решено переходом на `emptyDir` с уменьшенным retention.

## Что было сделано «как в продакшене»

- **Модульность.** Инфраструктура, K8s конфиги и приложение
  в разных репозиториях с независимыми пайплайнами.
- **Data-driven подходы.** Реестры Helm-чартов и Secret'ов
  вместо дублирующегося кода.
- **Секреты.** Ни один секрет не хранится в Git.
- **GitOps-принципы.** Все изменения через PR, никаких ручных
  правок в кластере.
- **Наблюдаемость.** Метрики, логи, аудит, алерты.
- **Отказоустойчивость.** Несколько реплик, распределение по
  узлам, rolling update.

## Направления для развития

Проект можно развивать в следующих направлениях:

1. **PersistentVolume для Prometheus.** Через managed node group
   или Thanos + S3 для долгосрочного хранения метрик.
2. **External Secrets Operator + Yandex Lockbox.** Централизованное
   управление секретами с автоматической ротацией.
3. **Argo CD.** GitOps-подход к деплою вместо прямого `kubectl apply`.
4. **cert-manager.** Автоматическое продление TLS-сертификатов.
5. **Service Mesh.** Istio или Linkerd для observability и mTLS.
6. **Cluster Autoscaler.** Динамическое масштабирование узлов.
7. **Отдельные node pool** для системных и прикладных нагрузок
   с taints и tolerations.
